四组独立生成图不能自动组成连续动画。足序表和脚掌标记只记录意图或位置，没有证明承重交接与腿的身份连续。第一帧眼距得到配准，也不能约束其余帧的颅骨、胸髋体积。此次使用的是所有帧共用的一次映射，问题不能归因于逐帧缩放。

均匀曝光本身可以用于好动画，但前提是相邻姿态的间距对应目标速度。此次直接把 16 张图平均分配到 640 ms，没有完成这个检查。只改播放速度无法补齐缺失的姿态，也无法修好模型漂移。

## 停止后仍奔跑：可重复的程序问题

1. 上轮隔离设备演示后，以 `state/session_id/project/message` 恢复当前会话，没有恢复 `turn_id`。执行记录可确认这个操作。
2. 旧状态机把“原编号未知，收到真实编号”当成“另一个旧回合”。因此 `running(无编号) → Stop(有编号)` 返回未应用，状态留在 running，无法随这次结束事件退出。两事件复现重复失败。
3. 另一个可复现路径是 `UserPromptSubmit → Stop → PostToolUse`：旧实现丢弃钩子来源，同一回合的迟到工具事件会重新开始奔跑。Interrupt 后也一样。

修复：允许未知编号采用首次观测到的编号；在 IPC 归一化中保留合法钩子名；Stop/Interrupt 结束回合后拒绝迟到的工具/权限活动，新的 prompt 可以启动下一回合。明确的手动状态演示仍可用。响应新增 `applied`，便于区分请求成功与事件被忽略；status 提供选中会话的回合编号。

`tests/test_daemon_lifecycle.py` 在真实 `event_from_hook → Daemon.process → direct_event → SessionStore` 边界复现，先失败后修复。包括未知编号、新 prompt 缺编号、同回合迟到活动、旧回合 Stop、下一回合恢复、显式手动状态切换。

**现场因果限制：** 上轮恢复方式与第一条复现完全一致，强烈指向它；但没有保留当时 Stop 的收件记录，不能声称已经证明该事件实际到达。钩子配置中有 Stop，Codex 会话记录也有任务结束；两者都不能替代收件证据。事件完全缺失以及跨回合无编号的事件，仍是 hooks 集成的信息限制，不以超时猜测工作结束。
