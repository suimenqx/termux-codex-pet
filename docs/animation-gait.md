# 秋田犬奔跑步态绘制与验证经验

本文记录本项目绘制 256 × 256 秋田犬奔跑帧时学到的步态知识、关键姿势安排和无截图验证方法。所有状态的画布、可见尺寸、源图生成和验收阈值统一见[动画图片规范](animation-assets.md)。后续更换帧图或制作其他四足动物动画时，先按本文整理动作，再用生产渲染路径验证；代码中的帧序、帧数和精确时序以 `codex_pet/animation.py` 为准，`codex_pet/art.py` 将逻辑帧映射为图像素材。

## 先确定动物怎么跑

快速奔跑要表现成奔跑步态，而不是把走路或对角小跑加快。犬类疾驰通常是不对称步态：同一对腿不是简单地左右同步摆动，前后肢也会在支撑、蹬地、腾空和落地之间错开。地面接触顺序会随犬只和速度变化；犬只也可能偏好某一侧作为领腿。因此，小尺寸角色可以稳定选择一个清楚的领腿方向，但不应把两只后腿画成完全重叠、镜像同步的单一动作。

设计时应先确定角色朝向、画面可见的近侧和远侧肢体，以及领腿侧，再确定脚掌的接触顺序。参考资料能帮助辨认步态模式，但单张照片或一种犬只的步态不应被当作所有犬只的固定模板。

## 把循环拆成可读的关键姿势

本项目用 8 个姿势表达一轮简化的犬类疾驰。姿势名是本项目的绘制和审计标签，不是完整的兽医运动学模型。

| 帧 | 阶段 | 绘制重点 |
| --- | --- | --- |
| 0 | `compression` | 身体收紧，四肢靠近身体，为后肢支撑做准备。 |
| 1 | `rear_support` | 后脚进入支撑，脚掌与躯干的相对位置清楚。 |
| 2 | `hind_drive` | 后肢向后蹬伸；近侧和远侧脚掌走不同轨迹。 |
| 3 | `suspension` | 短暂腾空，四肢离开支撑姿态，身体略微伸展。 |
| 4 | `fore_contact` | 前爪向前接触，形成下一段受力姿势。 |
| 5 | `fore_support` | 前肢支撑，后肢开始回收或在身后跟随。 |
| 6 | `recovery_tuck` | 四肢向身体下方回收，为下一轮蓄势。 |
| 7 | `loop_transfer` | 回到收身姿态；必须和帧 0 的轮廓及重心相接。 |

关键姿势要表达不同受力阶段。每帧都把所有腿伸开会像漂浮；每帧都让脚掌贴地会像快走；两只后脚如果始终叠在同一位置，远侧腿会看起来没动。让近、远脚掌保持可辨认的前后或上下差异，同时保留犬只身体紧凑的整体轮廓。

循环接缝属于动作的一部分。逐帧看完 0 到 7 后，还要专门检查 7 → 0：比较头部、髋部、身体高度和四只脚的位置。如果最后一帧只是一个新的大幅伸展姿势，下一帧突然回到收身，循环会产生明显抽动。旋转帧序号不能修复接缝；需要修改末姿势、首姿势或加入真正的过渡姿势。

## 本次遇到的问题与处理

| 问题 | 定位结果 | 修复或后续方案 |
| --- | --- | --- |
| 看起来像小跑，后腿不协调，远侧后脚像没动 | 早期审计只统计腿部矩形区域的轮廓变化；身体漂移、阴影和遮挡也会改变像素数，不能代表某只脚真的迈步。 | 使用 8 个不对称疾驰姿势；逐帧标注两只后脚，并相对橘色髋部测量路径。联系表用洋红和青色画出标记，审计同时检查脚掌可见性、移动范围及两条路径是否分开。 |
| 角色边缘出现红、黄、青绿等亮点 | PNG 帧里有低 alpha 像素，其 RGB 颜色仍保留原值；这是合法的未预乘 PNG 表示。旧渲染路径把 RGBA 原样写入 Termux:GUI 共享内存，插件再用 `copyPixelsFromBuffer()` 复制进默认按预乘 alpha 绘制的 Android `ARGB_8888` Bitmap。复制不做 alpha 转换，于是透明边缘的 RGB 被当成强颜色显示。重启旧代码不会改变这个格式不匹配。 | 已移除秋田帧的共享缓冲区路径，改为通过 `ImageView.setimage()` 发送 PNG，让 Android PNG 解码器在绘制前正确预乘 alpha；原始画作和四肢姿势不变。回归测试禁止秋田渲染再次创建 raw buffer；用户在设备上确认奔跑边缘的噪点消失。 |
| 新跑姿看起来太急 | 8 帧各 60ms，一轮 0.48 秒；在约 64dp 的小形象上，连续姿势切换显得过快。 | 已放慢到每帧 80ms，一轮 0.64 秒。先用 `tools/preview_animation.py` 检查真实帧序与时长，再用 `tools/audit_animation.py --state running --cycles 2` 检查两轮接缝和动作路径；设备端重启后运行 `codex-pet test`。 |
| 生成的动作表相邻格裁切或串入 | 整张动作表不保证每个角色都落在独立且对齐的格子里。 | 每帧按固定格子裁切成同尺寸文件，逐帧检查画布边界、透明边缘和动作顺序；不合格的裁切版不进入运行素材。 |
| 前脚看起来同步摆动，四肢配合不自然 | 原先的 8 帧虽有后脚错相，近侧与远侧前脚在多数姿势里却贴得很近；审计也只跟踪后脚，因此无法发现前脚的相位问题。 | 重绘同一角色的 8 格动作表，让前脚依次前伸、触地和回收，保持后脚分离；在运行尺寸上标注四只脚，新增前脚分离帧数与反向移动检查。 |
| 切换到奔跑时角色明显缩小 | 新动作表每格留白较多，初版导出时没有对照其他状态的可见轮廓面积；固定的 64dp 视图只会忠实缩放整个 256px 画布。 | 导出时以画布中心放大奔跑素材 1.18 倍，并检查 8 帧可见面积与待机帧的比例；同时保留透明边缘与循环接缝。 |

“已定位”和“已修复”要分开记录。此前的彩色边缘噪点来自共享缓冲区与 Android Bitmap 的 alpha 预期不一致，已通过使用 PNG 解码路径修复，当时没有重绘素材。本次四足协调问题则修改了奔跑素材，并扩展了脚掌审计。

### 彩色边缘噪点修复复盘

这次确认，问题出在显示链路，不在奔跑特效或跑姿素材本身。排查透明图时，不能只看像素的 RGB 数值：PNG 使用未预乘 alpha，低 alpha 像素即使保留鲜亮 RGB，正常合成后也几乎不可见。把原始 RGBA 直接显示在不匹配的缓冲区上，才会让隐藏颜色变成边缘亮点。

具体链路是：`rgba_icon()` 返回 PNG 解码后的直通道 RGBA；旧 GUI 把它原样写进 Termux:GUI shared buffer；插件将共享内存内容直接 `copyPixelsFromBuffer()` 到 Android `ARGB_8888` Bitmap。该 Bitmap 会被 View 系统按预乘 alpha 绘制，但复制像素没有做 `RGB × alpha / 255` 转换。因此本应很淡的边缘颜色以接近不透明的亮度出现。播放速度和重启都不改变这条链路，单纯重启也无法修复。

排查中试过从帧图上直接清点、按连通区域删除、扩大 alpha 轮廓或重新生成帧。这些方法没有修复缓冲区契约；轮廓清理还可能锯齿化毛发边缘，整帧生成则可能改变跑姿。最终保留全部原始帧，改为 `ImageView.setimage()` 发送 PNG，由 Android 解码时转换 alpha，再交给 View 绘制。此次设备上的奔跑状态已由用户确认边缘干净，说明修复落在真正出问题的环节。

以后如果恢复共享缓冲区，必须先把每个颜色通道转换为预乘值，例如 `(channel * alpha + 127) // 255`，并保证 alpha 通道和 RGBA 字节顺序符合接收端约定；仅凭源图放大检查或离线原始 RGB 统计不能证明运行时边缘正确。当前回归测试禁止秋田渲染调用 raw buffer，离线审计则通过预乘 alpha 的缩放流程查看联系表；设备端还运行了 `codex-pet restart` 和 `codex-pet test`，GUI 保持 ready，日志没有新增错误。

## 绘制帧时保持角色稳定

- 固定观察角度、角色朝向、画布大小、头身比例和表情。动作主要来自四肢与躯干姿势变化，不要让每帧重新设计一次角色。
- 统一脚下基线和髋部的大致锚点。腾空阶段允许整体上下变化，但头、胸、臀不能随机缩放或漂移。
- 近侧和远侧腿要能分辨。可用遮挡顺序、少量明暗差异和不同的脚掌轨迹表达深度；不要依赖几乎看不见的细节。
- 保持脚掌形状完整且留在 256 × 256 画布内，背景透明。缩到约 64dp 后仍要能看清腿部，不要只在原图放大时才成立。
- 在透明棋盘格和浅、深纯色底上检查经过正确 alpha 合成的轮廓。若彩点只出现在设备、正确合成的离线预览却干净，先核对解码器、像素顺序和预乘 alpha 契约，不要直接改帧图；只有在正确合成结果里仍可见的瑕疵才需要修边，并保护角色轮廓和四肢姿势。
- 若使用生成的动作表，逐格裁切后检查画格边界、透明边缘和邻格串入。动作表可能有裁切偏移或角色越界；不能把整张表直接当作运行素材。
- 把生成工具当作姿势草稿来源。逐帧统一角色尺寸、落点、轮廓和动作顺序，再接入生产帧列表。

## 接入动画帧表

素材序号、状态帧数、逐帧时长和预览顺序必须一致。新增或替换帧时，保持文件编号连续，在 `animation.py` 更新 `AKITA_FRAME_COUNTS` 和 `AKITA_FRAME_INTERVALS`，并同步 `running.png` 这个单帧回退素材。`AnimationTimeline` 驱动 GUI，`playback_frames()` 为预览和审计生成同一套有限时间表；`art.py` 负责把逻辑帧映射到图像。为帧数、循环回到 0、计时和运行审计添加或更新回归检查，避免预览正确但运行时仍读取旧帧数。

## 用脚掌轨迹验证“腿真的在动”

仅统计某个矩形区域的像素变化不够可靠：身体移动、阴影变化或另一条腿经过该区域，都可能让统计值增加，却不能证明目标脚掌移动。本项目改为：

1. 在每个关键姿势上手工标记近侧和远侧的前后四只脚掌中心。
2. 从橘色髋部区域计算躯干锚点，测量每只脚相对髋部的位置，排除整张角色平移造成的假运动。
3. 在生产尺寸渲染图上叠加洋红色与青色后脚标记、绿色与橙色前脚标记，人工确认圆环确实落在对应脚掌上。
4. 检查脚掌标记周围的透明度和浅色像素，确认测量点仍在可见脚掌内。
5. 检查每只脚的水平、垂直范围和整周期路径长度，也比较每对脚的路径是否分开、是否存在方向相反的移动阶段。前脚还须在至少 5 个姿势中保持可读的间距。
6. 连续渲染至少两轮，检查帧顺序、播放时长和循环接缝。

当前运行审计使用 64dp 宠物尺寸、默认 3× 显示密度，并将 256px 素材经 `rgba_icon()` 和审计缩放流程渲染为 192px；四只脚的坐标与髋部锚点在 `tools/audit_animation.py` 中维护。第 1 帧远侧前脚被遮挡，不拿近侧脚掌冒充它的落点；远侧后脚有些姿势被阴影覆盖，所以按可见不透明像素检查，颜色阈值低于近侧脚。换图后必须重新检查和更新标记坐标，否则审计可能测到错误位置。当前阈值是回归检查的下限，不代表真实狗的步幅或关节角度标准。

当前奔跑动作表保存在 [`docs/artwork/running-gait-sheet.png`](artwork/running-gait-sheet.png)。每格有透明留白，避免脚掌跨格或裁断。用下面的命令重新生成运行帧；`running.png` 是第 0 帧的单帧回退图，也要同步复制。生成工具对每格独立取样，以预乘 alpha 方式缩放，避免毛发边缘出现亮色晕边；缩放前将动作表下排配准偏移 10px，使首尾和第 3→4 帧的头部位置接得上。所有姿势围绕画布中心放大 1.18 倍，使奔跑时的可见大小与其他状态接近。

```sh
python tools/prepare_running_frames.py docs/artwork/running-gait-sheet.png codex_pet/assets/akita/frames/running
cp codex_pet/assets/akita/frames/running/00.png codex_pet/assets/akita/running.png
```

运行审计：

```sh
python tools/audit_animation.py --state running --cycles 2 --density 3
```

工具会输出逐帧图、带脚掌标记的联系表和 `audit.json`。也可以生成使用生产帧序与时间表的浏览器预览：

```sh
python tools/preview_animation.py --state running --cycles 2
```

离线审计可以复现程序交给 GUI 的像素和帧时间，适合比较素材、追踪脚掌和发现循环接缝；它不能完全模拟 Android `ImageView` 的图像滤镜或人的实时观感。涉及 GUI 改动时，仍按 [架构文档的验证说明](architecture.md#verification-by-change-area) 重启并检查 Termux 运行状态。

## 本项目的播放节奏

奔跑帧使用 8 个姿势，每帧 80ms，一轮约 0.64 秒。增加姿势时应先确定整轮步频，再观察落地、蹬地和腾空的节奏；帧数增加但周期同时显著变长，角色会显得慢下来。本项目将播放从 60ms 放慢到 80ms，让小尺寸形象的动作更从容。GUI 动画时钟依据单调时钟推进，并跳过过期帧，避免阻塞后快速补播一串旧帧。若要调整相位时长，应根据每段支撑和腾空所需时间调整帧表，不要用任意降低整体帧率来掩盖姿势跳变。

## 参考资料

- [Planar Covariation of Hindlimb and Forelimb Elevation Angles during Terrestrial and Aquatic Locomotion of Dogs](https://pmc.ncbi.nlm.nih.gov/articles/PMC4517757/)：犬类步态测量研究，报告了横向疾驰及其腾空阶段特征。

- [Eadweard Muybridge, Plate 710: Dog galloping, white racing hound, Maggie](https://www.nga.gov/artworks/220618-plate-number-710-dog-galloping-white-racing-hound-maggie)：连续摄影姿势序列，可用来观察一个跑步周期如何展开。
